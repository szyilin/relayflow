## Context

覆盖 B1 / B2。探针确认 DocObject 的 updateById 生成 `SET body=?, content_version=? WHERE id=? AND deleted=0`，没有版本条件；打开 / 重命名传入完整旧对象即可覆盖正文。前端 `activeDocument` watcher 复制 body 到 draft，保存响应重建 activeDocument，会覆盖保存期间继续输入的内容；防抖函数执行时才读取当前文档，切换会丢失原草稿。

## Goals / Non-Goals

**Goals:** 元数据更新不会覆盖正文；每份草稿按上下文排队保存；慢响应不回退新输入；切换与关闭有明确的保存 / 放弃边界；冲突或失败保留可恢复草稿。

**Non-Goals:** 不实现 CRDT / OT、离线数据库、多人自动合并、历史版本产品、新编辑器或全站状态重构。不保证浏览器被强制杀进程后恢复仅在内存中的草稿。

## Decisions

### D1. 前端先冻结保存协议与状态

- 在既有 workspace-docs-library contract 中补充 UI 状态、CAS 与错误恢复矩阵，再实现 `web/` 页面 / store。单 change 顺序为前端 → 后端 → 联调，不另造页面或第二套 API。
- 草稿键为 userId + tenantId + objectId；每次编辑分配递增本地修订号。加载 generation 与保存 generation 分开，打开时可初始化，元数据 / 保存响应不能无条件重新初始化已脏正文。
- 保存状态至少区分：干净、待保存、保存中、失败、版本冲突。只有已确认修订等于当前修订且队列为空时显示“已保存”。

### D2. 每文档串行保存，事件发生时绑定文档

- 防抖保留约 1200ms，但回调捕获编辑时的上下文、objectId、修订号及正文副本；不能在定时器触发时改用另一个 activeDocument。
- 每文档最多一个请求在途，期间新输入保留为最新待保存修订；成功后用返回 contentVersion 发送下一份。一个文档的排队不污染另一个文档。
- 响应只确认对应请求快照、推进服务端版本；若存在更新草稿，不把旧 body / title 写回编辑器。迟到的加载、重命名或旧 generation 响应也不能重置新草稿。
- 失败响应保留内容与原 CAS 基线，提供显式重试；不能给旧 body 换上服务器最新版本号自动重试，从而覆盖其他编辑者。

### D3. 离开与身份边界

- 切换文档、返回列表或 SPA 路由离开：先 flush 并等待确认；失败时允许留在原文档重试，或明确放弃后离开，不静默清草稿。用户选择放弃是明确的数据丢弃行为。
- 浏览器刷新 / 关闭：脏队列触发标准 beforeunload 提醒；不承诺异步 HTTP 能在卸载时必然成功，不用固定延时或“已发送”冒充“已保存”。
- 登出 / 账号或租户切换按现有安全清理流程处理：撤销旧队列派发、取消客户端请求并忽略迟到响应，不用新 token 提交旧草稿，不向另一个身份显示旧内容。已经在服务器提交的请求不作伪回滚。
- 对已保存快照和本地草稿保留独立副本，避免对象引用变化使版本 / 内容错配。

### D4. 冲突恢复保留用户内容

`DOC_VERSION_CONFLICT` 不自动覆盖或直接刷新。保留本地草稿，提供复制 / 导出本地草稿的恢复途径，再由用户明确选择加载服务器版本或继续处理。加载服务器版本是可能放弃本地内容的操作，必须有明确提示。VIEW / 权限撤销 / 删除错误停止后续派发并保留可解释错误；不能绕过 ACL 强存。

### D5. 后端只更新目标字段

- 打开文档只更新 last_opened_at 与所需 audit 字段；重命名只更新 title 与 audit 字段。库 / 云盘及其他实际元数据写路径都审计一遍，使用 patch / 明确 SQL，不传完整旧 DocObject 回写。
- body 和 content_version 仅由正文保存路径更新，继续 `WHERE id AND content_version=expectedVersion` 的原子 CAS；metadata 读取 / 更新不递增、不降低正文版本。
- 保留既有租户、owner / EDIT / VIEW 和逻辑删除规则；CAS affected=0 仍返回已有冲突错误，不重置版本、放宽权限或增加“强制覆盖”参数。
- 同一所有者在另一窗口重命名 / 打开、另一个 EDIT 成员保存时，元数据与正文各自保留；并发测试必须覆盖这两个交错次序。

## Risks / Trade-offs

- Promise / 定时器假完成 → 使用可控延迟和失败夹具验证状态，不只检查 toast。
- 首个响应晚于后续输入 → 用修订 / generation 判定归属，测试返回后编辑器仍为最新内容。
- 身份切换时请求已在途 → 清理队列、阻止后续派发、忽略旧响应；不声称可取消已提交事务。
- 多人同时编辑 → 明确冲突并保留草稿，本轮不自动合并。

## Migration Plan

无需 Flyway、DO 字段、环境变量或新端口。实施时在既有 Vue / Nuxt UI / TipTap 与测试工具内完成，任何新增 npm / Maven 依赖仍须许可。发布安排用户先保存并刷新，避免旧脚本继续使用旧队列；回滚不修改现有文档版本或正文。内网验收无需外部服务。

## Open Questions

无阻塞规划的问题；默认采用串行队列 + 显式冲突恢复。草稿的物理设备崩溃后恢复属于未来离线持久化范围，不承诺此次实现。
