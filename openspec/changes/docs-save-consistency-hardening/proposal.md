## Why

P1 扫描项 B1 / B2：文档打开 / 重命名把已读取对象整行写回，生成 SQL 会更新旧正文和旧版本，绕过正文保存的 CAS；前端保存响应又会用旧请求正文覆盖继续输入的草稿。需要同时保护数据库更新和客户端草稿，覆盖慢响应、切文档与版本冲突。

## What Changes

- 打开记录、重命名及其他文档元数据更新仅写允许的字段，正文 / content_version 只能经版本条件更新，不被元数据更新回滚。
- 前端按账号 / 租户 / 文档维护草稿修订号和单文档保存队列，保留最新待保存内容；旧响应仅推进已确认版本，不覆盖后续编辑。
- 防抖保存绑定编辑发生时的文档；切文档 / 路由离开先 flush 或明确提示保留 / 放弃；刷新关闭有未保存提醒。
- 保存失败和版本冲突保留草稿并提供明确恢复操作；“已保存”只在当前草稿收到确认且队列排空后显示。
- 保留现有 owner / VIEW / EDIT、TipTap JSON 和 CAS 契约，不引入多人实时合并、离线数据库或新编辑器依赖。

## Capabilities

### New Capabilities

无；增强现有云文档读写可靠性。

### Modified Capabilities

- `docs`：元数据更新不触碰正文、草稿保存顺序、离开保护、冲突恢复与账号 / 租户边界。

## Impact

- 类型：**用户可感知切片，单 change 前端优先**；tasks 按前端 → 后端 → 联调排列，实施时先在既有 docs contract 中冻结保存 / 冲突与离开行为。
- Java：docs-biz 的 document / library / drive 及实际写入 doc_object 的元数据路径；前端仅 `web/` 的 docs 页面、store、编辑器相关状态。
- 保持现有 GET / PUT 文档与重命名路径和响应，不新增端口 / 环境变量、Maven / npm 依赖、Flyway 或 DO 字段；不改部署编排。
- 自部署：无数据迁移；部署时让正在编辑的用户先完成保存，不能把新草稿状态与旧页面脚本混用。回滚保留原数据与 content_version，不执行版本重置。
- 不纳入知识库、新文档格式、编辑器性能重构或 P2 质量基线。已按前端优先实施；验证见 verification.md。
