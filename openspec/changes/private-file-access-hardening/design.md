## Context

覆盖 A1。`resolveMemberDownload` 调用 `resolveAdminDownload`，`requireFile` 仅限定 tenant。现有 infra spec 要求私有文件的 JWT + 权限 / 业务授权；现有 doc_object 文件绑定可复用，IM 消息文件尚未统一写绑定。平台修复不新增页面，先满足当前有效身份规则，再在业务域验证文件访问。

## Goals / Non-Goals

**Goals:** 已确认上传的私有文件只向当前有权主体签发新下载 URL；保持合法本人预览、IM 附件与云盘下载；历史绑定可预演补齐；禁止通过伪造附件引用“洗出”读取权限。

**Non-Goals:** 不改 public 文件匿名模型、管理员权限体系、对象存储数据搬迁；不处理上传确认幂等 / 并发（C2）、会话序号（C1）或撤销已经签出的 S3 URL；不把所有业务数据搬到 infra。

## Decisions

### D1. 成员与管理员下载走不同授权入口

1. 检查当前有效用户 / tenant，再查询未删除文件；跨租户记录不返回存在性信息。
2. `public` 保持现有公开路径；管理员私有下载只在既有 `/admin-api` 及 `infra:file:download` 下放行，不能把管理员角色当作 `/app-api` 的通用绕过。
3. 无任何业务绑定的 private 文件，仅其创建者可用于上传完成后的本人预览。creator 缺失不自动认为全员可读。
4. 有业务绑定的 private 文件，要求至少一个已识别绑定的当前业务授权通过。此时原始 creator 不能绕过对象所有权转移、退群、撤回或删除。
5. 无可读绑定返回明确 FILE_ACCESS_DENIED；未知 bizType 不放行。授权异常视为不可读 / 明确失败，不能转用管理路径。

已有签名 GET 最长仍受既有 15 分钟 TTL 限制：撤销业务授权后拒绝新签名，已发 URL 可能继续可读至过期。若未来要求每个字节即时撤销，应另行设计代理下载，不在此轮承诺。

### D2. infra-api 授权 SPI，业务域保有真源

- infra-api 定义基于 tenantId / userId / fileId / bizType / bizId 的授权 SPI / DTO；由 IM、docs 的 biz 实现。infra-biz 按 bizType 调用注册策略，不新增 `infra-biz → im-biz/docs-biz`，不直连 im_* / doc_*。
- IM 使用 `im_message` 绑定：消息仍存在、未撤回、当前内容仍引用该 fileId，且当前用户按原消息 / 会话规则可读，才授权。退群、编辑移除附件、撤回、删除均不能依赖旧绑定继续放行。
- docs 复用现有 `doc_object` 绑定：FILE 对象 ACTIVE / 未逻辑删除，用户是当前合法所有者；未来类型的授权必须显式扩展，不能把 RICH_DOC 的分享 API 直接套到 FILE。转移后旧上传者不保留绕过权。
- 一个 fileId 可有多个可信引用，可读性取有效授权并集；不会因为某个引用失效而错误拒绝另一个仍合法引用，也不把未知绑定当作全员授权。
- 策略只访问本域真源或合法 *-api，不递归调用同一成员下载方法，避免依赖循环与无限授权递归。

### D3. 创建绑定前已具备引用资格

- IM 发送、转发、编辑及实际使用私有文件的 Bot / sticker 路径先验证调用主体已有文件读取资格，再持久化消息与可信绑定；仅把任意 fileId 插入自己的会话不能创造权限。
- bizId、bizType、tenantId 由服务端领域流程生成；客户端的 file block 不作为授权证据。FileApi.bindFile 是内部投影入口，不新增可任意调用的 HTTP 绑定接口。
- 普通路径在业务事务内先持久化资源与绑定再 ACK / 提交，失败整体回滚。同步契约放在 infra-api，各域仅调用 api；不能用异步 best-effort 绑定制造已确认资源与授权投影不一致。
- docs 上传入盘沿用创建者 / 当前文件可引用性校验，绑定不替代对象 ACL。保持同 fileId 多引用、幂等唯一索引和文件原名 / key 不变。

### D4. 历史文件补绑定先于严格验收

- 各领域分页枚举自己的真实历史引用，通过 FileApi 幂等写入现有 infra_file_binding；默认 dry-run，输出计数 / 异常 ID，不输出内容正文、凭据或签名链接。
- IM 覆盖历史 file / image / 实际私有 sticker、转发与仍有效消息；docs 核对既有绑定。跨租户、不存在文件、不能确认的引用进入异常清单，不扩大授权；可疑历史引用由操作者核对。
- 在测试副本验证重跑、分批中断恢复与授权结果，确认正常附件覆盖后再升级严格校验。运行时不能为解决漏绑定而默认给同租户全员放行。
- 无需新表 / 新依赖；需要新迁移或新公开操作端点时先说明并另获确认。

## Risks / Trade-offs

- 一刀切 creator-only 会破坏聊天附件 → 明确可信绑定策略与历史投影。
- 已发签名 URL 仍有 TTL → 文档明确边界，新增请求即时按现有 ACL 判断。
- 文件转发可被用作越权入口 → 先验证已有读取资格，再允许生成新引用。
- 旧消息 / Bot / 表情引用不齐 → 首个实施任务盘点所有私有消费者；不能只验正向上传下载。

## Migration Plan

先完成成员身份门禁；测试副本做 dry-run / 备份 / 幂等补绑定；再部署严格授权并回归旧 IM 附件、云盘转移 / 删除和 public 头像。保留绑定不改变对象存储数据。回退优先禁用有缺陷的业务入口并修正策略，不通过全员开放 private 文件恢复可用性。

## Open Questions

无阻塞规划的问题。实施中若发现其他实际 private 消费域，应先盘点并在同一授权契约内补策略；新增业务能力仍须另立项。无新端口 / 环境变量，离线部署使用现有 DB / 存储即可。
